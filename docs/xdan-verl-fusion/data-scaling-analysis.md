# A 组 RL 数据扩展分析：数量、领域与其他维度

日期：2026-10-03 · 分支 `worktree-xdan-verl-fusion` · 依据：ga103 前 8 步实测、本仓库配置和脚本、公开文献（见文末）。
立场：只读分析，不改训练和数据。凡是估算都标"估"，并写出假设。

---

## 1. 结论先行

1. **数量现在不是瓶颈，信号密度才是。** 100 步 × 8 组 = 800 个被接收的 prompt。数据池里 Code 2598 加 Harbor 500，一轮连 1 个 epoch 都用不完（估：抽取约 1.2–1.5K 个 prompt，覆盖池子 40–50%）。在步数不变的前提下，把 batch1 的 1851 题加进去，只改变分布，不增加训练量。15K 全量池的价值在于"可供筛选的候选池"，而不是"训练量"。
2. **ga103 实际上是一次"只有 Code 的 RL"，却要拿 TB2.1 来验收。** 前 5 步被接收的组里 Code 38、Harbor 2。stage1 Harbor 在 mimocode 下得分 0.94，几乎全部被 DAPO 过滤掉。这样 TB2.1 能拿到的同分布训练信号接近 0，就算出现增益，也只能来自迁移。Code holdout100 和训练集同分布，+3pt 更容易拿到，但它说明的问题也更少。
3. **最大的单点浪费是 64K 上下文。** DSH 约 35%、mimocode 约 25% 的会话因为上下文用满而得 0 分。MiMo 官方 Code 配方的 `max_response_length` 是 253952（约 256K），见 `recipes/code/config/train.yaml:136`。SFT 模型的轨迹长度是按更大的预算形成的，现在硬截到 64K。结果有三个：大量本来可解的轨迹变成 0；这些最长的轨迹又拖长了步时（长尾）；接收组里有相当一部分"混合"信号，教的其实是"写短一点"，而不是"解得更对"。
4. **评测的统计功效不足以判定 +3pt。** 估算：89 题 × mean@4 配对比较，标准误约 2.5–2.7pt，+3pt 只有约 1.1–1.2 个 SE。再乘上 2 个评测集 × 2 个 harness × 3 个 checkpoint 的多重比较，靠噪声"命中一次 +3pt"的概率不低。SFT 基线至今没跑，step 25/50 的判定实际上没有依据。
5. **第二轮 Top 3**（详见 §6）：
   - ① 测量先行：SFT 基线、功效分析、预注册主指标，再把 ga103 的 rollout 拆成按任务的通过率和失败原因；
   - ② 难度校准的 Harbor 池：先用 200 题做 pilot，再决定是否全量筛，然后把 Harbor 占比提到 40–50%；
   - ③ 上下文预算治理：128K，或者对上下文用满的轨迹做掩码，或者调整 harness。
   这三项都比"加数量、加领域"便宜，回报也更确定。领域扩展（B 组并入）放到第三轮以后，并且要以 A 组在 TB2.1 上有正证据为前提。

## 2. 对当前方案的审慎挑战

### 2.1 目标层面（XY 问题）

- **X（真实目标）**：在独立评测上可信地超过 SFT。
- **Y（提出的手段）**：扩充数据的数量和领域。
- 从 ga103 的证据看，限制 X 的因素依次是：
  - (a) 没有基线，判定口径不可靠；
  - (b) 难度错配，Harbor 实际上没有参与训练；
  - (c) 上下文预算，25–35% 的采样被浪费，还带偏信号；
  - (d) 吞吐，74 小时只覆盖 800 个 prompt。
- Y 对这四项都没有直接作用。在 (b)(c) 没解决之前加数量，新数据会以同样的比例被浪费掉。

### 2.2 与官方配方的规模差距（实测配置对比）

| 项 | MiMo 官方 Code（`recipes/code/config/train.yaml`） | ga103（`launch_group_a.sh`） | 比例 |
|---|---|---|---|
| response 长度 | 253,952 | 61,440 | 约 1/4 |
| N | 16 | 8 | 1/2 |
| batch（prompt 数） | 32 | 8 | 1/4 |
| 步数 / epoch | 200 / 6 | 100 / 1 | 1/2 |
| 每步轨迹数 | 512 | 64 | 1/8 |
| 总轨迹数（被接收的部分） | 约 102K | 约 6.4K | **约 1/16** |

官方配方 200 × 32 = 6400 个 prompt，相当于对 Code 约 2.7K 题过了约 2.4 遍。可见**多 epoch 复用一个适中规模的题池是常规做法**；需要的是"可学的题"，不是"更多的题"。参考 MiMo-V2-Flash 的报告，旗舰模型的 code agent 数据是 90K 真实题加 30K 合成题，比我们这一轮的消耗量大两个数量级。这说明大规模数据只有在大算力下才有意义。我们在 4 卡、70 小时这个预算里，消耗量才是硬约束。

### 2.3 "被接收的组几乎都是 mid" 这句话是同义反复

DAPO 只接收奖励不全相同的组，所以被接收的组必然是"mid"，这句话本身没有信息量。真正需要看的是两件事：

1. 被接收组的通过率分布（1/8 … 7/8）；
2. **组内失败的原因构成**：答错、上下文用满、超时、infra。

如果一道题组内 4 条成功、4 条因上下文用满失败，模型学到的主要是"缩短轨迹"。这对 64K 评测确实有用，但不是解题能力。

### 2.4 DAPO 会主动偏向两类"伪中等难度"的题

- **flaky verifier**：奖励带随机性，组内天然混合，DAPO 正好把这类题全部收下。
- **长度型失败**：任务可解，但时常撞上上下文上限。

两者都会制造"有梯度但方向不对"的样本。oracle 审计只跑了一次 nop/oracle，**检测不出 flaky**。

### 2.5 评测口径的问题

- 估算的假设：每题组内方差 p(1−p) 平均约 0.10–0.15（存在大量 0/1 题，所以不大），两模型独立采样，配对差的 SE = sqrt(2·p̄q̄/k/n)。
  - TB2.1：n=89，k=4，SE ≈ 2.4–2.9pt；
  - holdout100：SE ≈ 2.2–2.7pt；
  - 要在 95% 置信度下检出，大约需要 +5pt。
- k 从 4 提到 8，SE 下降约 29%。
- 成功标准是"任一评测 +3 且另一个不回退"，同时在 25、50、100 三个点看，每个点还有 2 个 harness，这是典型的 forking paths。建议**预注册**：主指标只取一个，例如 TB2.1 在训练所用 harness 下、最终 checkpoint 的配对 bootstrap；其余作为次要指标。
- 评测也是 64K（`launch_eval_a.sh:33`）。如果 RL 后 +3pt，需要拆开看：有多少来自"上下文用满率下降"，有多少来自"完成的轨迹里正确率上升"。后者才是能力。建议加做一次 128K 评测作为对照（只做 SFT 和最终 checkpoint 两个点）。

### 2.6 harness 选择缺一个前提

DSH 和 mimocode 各占一半采样，但用户最终在什么 harness 下用这个模型、TB2.1 按什么 harness 报分，这些没有定。DSH 的上下文用满率更高（35% vs 25%），裸通过率更低（0.47 vs 0.54）。如果产品侧只用其中一个，另一半预算的收益不确定。见 §7 Q2。

### 2.7 小结：方案能否达标

- 估计 **Code holdout100 有一定概率出现正向变化**：同分布，接收组以 Code 为主。但能否越过噪声，取决于 k 和最终增益幅度，我给不出可信概率。
- **TB2.1 达到 +3pt 的可能性偏低**：同分布信号接近 0，评测功效也不足。
- 这个判断基于 8 步数据，置信度中等。

## 3. 数量扩展

**原则：数量是筛选器的输入，不是训练量的输入。** 题池需要多大，由"计划步数 × 每步组数 ÷ 接收率 ÷ 计划 epoch 数"倒推：

- 200 步，接收率 0.7，2 个 epoch：200×8/0.7/2 ≈ **1.15K 道可学题**（0 < p < 1）；
- 加上 Code，A 组可学题总量做到 **2.5–3.5K** 就足够支撑下一轮。

15K 全量池留作难度筛选的候选库，以及第三轮的储备。

### 3.1 分阶段计划

| 阶段 | 动作 | 规模 | 成本（估） | 进入下一步的条件 |
|---|---|---|---|---|
| Q0（免费） | 从 ga103 的 `ROLLOUT_DATA_DIR` 和 DAPO 丢弃组里，按任务回收通过率（N=8，分 harness、分失败原因），产出 `task_difficulty.jsonl` | 约 1.2–1.5K 题 | 只用 CPU 脚本 | 得到 Code 题的 easy / mid / zero 分布 |
| Q1 pilot | batch1 随机抽 200 题，mimocode 只做推理（不训练），k=4 | 800 条轨迹，约为 ga103 一轮的 10% | Modal 约 800 条 × 单条成本；GPU 可利用 ga103 的空闲或第二台 pod | 得到 batch1 的 easy 占比 f_easy |
| Q2 筛选 | f_easy > 25%：全量 1851 题按序贯 k=2 筛（2/2 剔除，0/2 抽样保留，1/2 保留）。f_easy ≤ 25%：不预筛，直接进训练，交给 DAPO | ≤ 3.7K 条轨迹 | 约为 ga103 的 40% | 可学 Harbor 题 ≥ 800 |
| Q3 第二批 | 只有当第二轮计划超过可学池 2 个 epoch 时，才从 15K 中再选 2000 题（分层：source、类别、语言、`difficulty` 字段），再 build 和审计 | 2000 题 build + oracle 各 1 次（不跑模型） | 主要是镜像构建；batch1 的 build 成功率 99.3%、审计通过率 93.2% 可作参考 | 第二轮在 TB2.1 上已见正向信号 |

**为什么 25% 是阈值。**

- 预筛每道题花 k=2 条轨迹。
- 不预筛时，一道太简单的题在训练里白耗 N=8 条，还会拉长步时（colocate 模式下这些采样占着 GPU）。
- 预筛划算的条件是 8·f_easy > 2，也就是 f_easy > 25%。
- stage1 Harbor 在 mimocode 下得分 0.94，明显超过这个阈值；batch1 是按 hash 随机抽的，没有经过 ladder 偏置，可能难得多，所以先做 pilot。

**用哪个 harness 判定"太简单"。** 用更强的 mimocode 判"太简单"，用训练实际的 harness 混合判"太难"，这样比较保守。按 Polaris 的经验，只剔除 8/8 的题效果最好，过度激进地只留难题反而有害。

### 3.2 怎么验证数量扩展有效

- **训练侧先行指标**（每步可见）：
  - Harbor 被接收组的占比从约 5% 升到 30% 以上；
  - 全对、全错组的占比下降；
  - refill 次数和步时下降；
  - 按来源拆分的 grad_norm 都不为 0。
- **评测侧**：TB2.1 和 eval-set-v1 的配对差。eval-set-v1 有 78 题，和 Harbor 同源，附带基座逐题成功次数，可以当作便宜的中间评测，看是否方向一致。
- **对照**：至少保留一条"不加 Harbor 新池"的对照。可以直接用 ga103 的同步数 checkpoint，不需要重跑。

### 3.3 风险与对策

| 风险 | 具体表现 | 对策 |
|---|---|---|
| 评测污染 | deny list 按名字匹配，抓不到改写或派生的题。terminal-lego 是合成数据，种子来源未核实；swe-rebench-v2 可能和 SWE-bench Verified 同 repo | ① 对 instruction.md 和 tests 内容做 MinHash/n-gram 近重复检测，对比 TB2.1、eval-set-v1、各 holdout；② 和 SWE-bench Verified 做 repo 级排除（DeepSWE 的做法）；③ 核实 terminal-lego 的种子是否来自 TB 系列 |
| verifier 假阳性（可 hack） | 公开审计：SWE-bench Verified 49 题样本中 28.5%、R2E-Gym 20 题中 25.0%，可以被错误补丁通过（样本小，只能当量级参考）。nop=0 / oracle=1 只证明测试"非空、可通过"，不证明"错解不过" | ① 每 10 步抽查 reward=1 的轨迹，按规则标记改动了 tests、conftest、CI 配置或 verifier 依赖的情况；② 如果训练 reward 上升而 eval-set-v1 持平，立即排查；③ 第三轮再考虑做 LLM 对抗补丁审计 |
| flaky verifier | 被 DAPO 优先收下（§2.4） | oracle 跑 3 次，任何一次结论不一致就剔除；训练中把"同一道题通过率在两个 epoch 之间大幅跳变"列为告警 |
| 镜像构建成本 | swe-rebench-v2 多语言镜像体积大；Modal 缓存 | 沿用 `build_images.py` 的可续跑机制；只 build 筛选后的题 |
| Modal 成本 | 筛选和评测的轨迹数可以和训练相当 | 每个阶段先报预算，pilot 之后再批；所有成本按"轨迹数"记账，再用账单换算成美元 |
| DAPO 过滤 | 太简单（全对）浪费采样，太难（全错）也浪费 | 预筛加训练中的在线通过率追踪：epoch 结束时剔除 8/8 的题（Polaris 的动态更新） |

## 4. 领域扩展

**先重新定义"领域"。** 对于 TB2.1 这个目标，真正有用的领域多样性，是**终端和 SWE 内部的任务类别**。TB2.1 覆盖 16 类：软件工程、安全、科学计算、数据科学、游戏、调试、系统管理等。MiMo 的产品域（Cyber、General、Webdev、Music）不是这个意义上的领域。

### 4.1 分层建议（按优先级）

| 层级 | 内容 | 来源 | 时机 | 理由 |
|---|---|---|---|---|
| D1：A 组内部类别多样性 | ① terminal 类题目按类别分层，对齐 TB2.1 的类别分布（只对齐分布，不碰题目）；② swe-rebench-v2 按语言分层；③ 设上限，防止单一类别或 repo 占比过高（现在 SWE 是 30 题/repo，terminal 没有上限） | 15K 全量池的 index（`source`、`category`、`difficulty`） | 第二轮，和 §3 Q2 一起做 | 便宜，同契约，零工程 |
| D2：Cyber（ARVO）进入 A 组矩阵 | 漏洞复现和修复，与 TB2.1 的安全类有重叠 | baseline 线已有 900 训练 + 100 holdout | 第三轮，前提是 D1 后 TB2.1 有正信号，并且安全类是短板 | 需要把 verifier 从 ArvoAgentLoop 里解耦出来（约数天工程），不能白做 |
| D3：General、Webdev、Music | 继续作为 B 组专家，独立训练 | baseline 线 | 不并入 A 组 | 和 TB2.1、Code holdout 的迁移路径弱；4h 档 Music SFT 0.460 → RL 0.436（噪声），目前没有 RL 增益的证据 |
| D4：整合 | MOPD 或路由 | — | 两边都有正证据之后 | 方案里已记录 MOPD 在 9B 上有负面先例（−0.172） |

外部可选来源（D1 不够时再用；用之前都要先过一遍 §3.3 的污染检测）：

- SWE-rebench V2：32K+ 个带预构建镜像的题，20 种语言；你们的池可能已包含其子集，需要核对；
- R2E-Gym：DeepSWE 用了 4.5K 题的子集，做了 repo 级去污染；
- SWE-smith、SWE-Gym；
- 终端合成数据：Endless Terminals、Nemotron Terminal-Corpus（注意它主要用于 SFT）、CalibForge。CalibForge 的"多求解器校准"思路值得借鉴，但它的增益里有多少来自 RL、多少来自 SFT，我没有核实。

### 4.2 怎么验证领域扩展有效

- 每个领域或类别都要有自己的 holdout，训练日志按领域拆分 reward 和接收组数。
- 主指标仍然是 TB2.1。进一步按 TB2.1 的类别拆分配对差，看增益是否出现在新增类别对应的评测类别上。这是"迁移来自新领域"的最直接证据，但每类题数很少，只能看方向。
- 遗忘检查：Code holdout100 不回退。

### 4.3 领域干扰风险

- **batch 太小**：每步只有 8 个 prompt。混入 4 个以上的领域后，每个领域每步只有 1–2 组，梯度方差很大。如果要混，就按领域**固定每步配额**（分层 batch），不要按数据量的自然比例。或者把 batch 提到 16 以上，这取决于吞吐，见 §5。
- **奖励尺度和稀疏度不同**：Webdev 的视觉打分是连续的，Code、Harbor 是 0/1。`prompt-mean` 加上不按 std 归一化，会让连续奖励域的 advantage 分布和二值域不一样，需要分开监控。
- **长度分布不同**：领域之间长度差异大，会改变 `prompt-mean` 下各领域在 token 层面的权重。
- **工程耦合**：B 组的 judge、grader、MCP 服务任何一个抖动，都会卡住整个 step（方案已经指出）。这是"只在 A 组内部扩展领域"的硬理由。

## 5. 其他维度（按"预期收益 ÷ 成本"排序）

| 排名 | 维度 | 证据 | 建议 | 成本 |
|---|---|---|---|---|
| **0（前提）** | **评测功效与口径** | SFT 基线未跑；SE 约 2.5pt；存在多重比较 | 尽快跑基线；TB2.1 用 k=8；预注册主指标；用配对 bootstrap；加一次 128K 评测作对照 | 1 次评测 |
| **1** | **难度校准 / 在线课程** | Harbor 得分 0.94，几乎全被过滤；全错组占 20–29% | §3 的 pilot 和筛选；训练中在线追踪通过率，每个 epoch 剔除 8/8；全错的题限量保留（每步 ≤ 1 组），留作"阶梯" | 低到中 |
| **2** | **轨迹长度与上下文预算** | 25–35% 因上下文用满得 0；官方是 256K | 先诊断：上下文用满的轨迹里，同组有成功者的占多少？再从三个方向里选（见 §6 ③） | 低到中 |
| **3** | **verifier 与奖励质量** | 只审计过 nop/oracle；公开审计显示 SWE 类 verifier 可 hack 比例为两位数 | oracle 跑 3 次剔除 flaky；规则化抽查 reward=1 的轨迹；全错比例高的难题可以考虑 FAIL_TO_PASS 部分得分（有 hack 风险，只在 A/B 实验里用） | 低 |
| **4** | **吞吐与 on-policy 新鲜度** | 每步 44.5 分钟；冒烟期 GPU 空闲 26–43%；步时被最长轨迹决定 | ① 挑入 `0fab9666`，切到 separate_async 或 partial rollout；② 上下文治理本身也能削长尾；③ `MAX_OFF_POLICY_THRESHOLD=2` 已经允许轻度 off-policy，可以评估放宽到 3–4 | 中（工程） |
| **5** | **数据复用（多 epoch）** | 官方约 2.4 个 epoch | 可学池做 2–3 个 epoch，比追加新题更划算；监控每个 epoch 的同题通过率，防止过拟合到具体 repo | 零 |
| **6** | **harness 多样性** | DSH 和 mimocode 各一半，两者表现不同 | 先回答 §7 Q2。如果产品只用一个，训练以它为主（≥ 75%），另一个只作为正则；如果都要，就保留 step-hash，并按 harness 分别评测 | 零 |
| **7** | **任务类型和环境多样性** | 见 §4 D1 | 放在难度校准之后 | 低 |
| **8** | **课程顺序（先易后难）** | 已有在线过滤时，静态排序收益有限 | 不单独做 | — |

难度排在上下文之前，是因为难度直接决定 Harbor 这个"TB2.1 同分布来源"能否参与训练。上下文问题影响的面更大，但先要诊断它是真失败还是被截断。两者应在第二轮同时处理。

## 6. 第二轮 Top 3 行动

### ① 测量先行：基线、功效、失败分解

- **做什么**：
  1. 租第二台 pod（或者等 ga103 到 step 25 时插空），跑 SFT 基线评测：TB2.1 用 k=8，holdout100 用 k=4，两个 harness 都跑。
  2. 写预注册文档：确定主指标、判定阈值、检验方法。
  3. 写一个 CPU 脚本，解析 ga103 的 rollout：
     - 按任务算通过率；
     - 失败原因拆成答错、上下文用满（区分同组有无成功者）、超时、infra；
     - 统计步时的长尾由哪类轨迹构成。
- **成本（估）**：
  - 评测：(89×8 + 100×4) × 2 harness ≈ 2.2K 条轨迹，GPU 约 8–12 小时，按 $8/h 约 $70–100，另加 Modal；
  - 脚本：约 0.5 天。
- **收益**：step 25/50 的判定变得可信；直接决定 ② 和 ③ 的方向和力度。避免 70 小时的训练成本花出去却无法判断结果。
- **验证**：基线分数的置信区间宽度符合预期；失败分解覆盖 ≥ 95% 的会话。

### ② 难度校准的 Harbor 池和配比调整

- **做什么**：
  1. 按 §3 Q0–Q2 执行：先回收 ga103 的通过率，再做 batch1 pilot（200×4），按 f_easy 决定是否全量筛；
  2. 筛选的同时做三件质量检查：oracle 跑 3 次、MinHash 去污染、SWE 的 repo 级排除；
  3. 组成第二轮数据：Code 剔除 8/8 后的部分，加上 Harbor 可学题 800–1500 道，Harbor 占比 40–50%，每步分层固定配额；
  4. stage1 中通过率 ≥ 7/8 的题移出。
- **成本（估）**：pilot 800 条轨迹；全量筛 ≤ 3.7K 条；工程约 1 天。
- **收益（估）**：Harbor 被接收组的占比从约 5% 升到 30–45%，TB2.1 的同分布信号从接近 0 变为主力；refill 减少，步时下降。
- **验证**：训练侧看 Harbor 接收组占比和 grad 拆分；评测侧看 eval-set-v1、TB2.1 的配对差，对照 ga103 同步数的 checkpoint。

### ③ 上下文预算治理

- **做什么**：先看 ① 的诊断结果，再从下面三项里选一项或组合：
  - **a. 训练和评测提到 128K。** 先做 1 步显存和步时测试。4×96GB、TP4、动态 bsz 是否能放下，需要实测，官方 256K 是在 32 卡上跑的。
  - **b. 对上下文用满的轨迹做掩码。** 参照 DeepSWE 的 compact filtering：对上下文或超时截断的轨迹做 loss mask，避免把"预算不够"当成负例。仓库里现有的 `deep_failure_mask` 是按轮次截断负 advantage 的实验通道，语义不同，不能直接拿来用，需要新增一个开关。风险是失去对"无效冗长"的惩罚，所以只掩码"同组有成功者"以外的情况，或者跑一次 A/B。
  - **c. harness 层面。** 如果 Q2 的答案是"产品以 mimocode 为主"，就降低 DSH 的占比，因为它的上下文用满率更高。也可以评估 harness 的上下文压缩或摘要能力。
- **成本（估）**：a 是 1–2 步测试，步时可能上升；b 约 1 天工程加 CPU 单测；c 只是改配置。
- **收益**：25–35% 的采样恢复成有效信号，长尾步时缩短，同时也能看清"能力增益"和"长度压缩"各占多少。
- **验证**：上下文用满率、接收组里因长度失败的占比、步时 P90，以及 64K 和 128K 两种评测的分数差。

暂不进 Top 3，但应该排进去的：吞吐（separate_async，加上 `0fab9666`）。它不增加数据，但决定了在同样的钱下能跑多少步。建议作为第 4 项，和 ③a 一起评估。

**关于 ga103 本身**：不建议中途停下或改数据，因为那样会破坏这次对照。建议让它跑到 step 25 或 50，作为"不处理难度和上下文问题"的对照臂。step 50 的停训判定，改为在 ① 完成之后，按预注册口径来做。

## 7. 需要用户决策的问题

1. **主指标选哪个**：TB2.1 还是 Code holdout100？建议定 TB2.1 为主，因为 holdout 是同分布的，说服力较弱。这个选择决定第二轮的 Harbor 占比。
2. **产品和评测用哪个 harness**：mimocode、DSH，还是两个都要？这决定 harness 的配比，以及 DSH 是否值得承担更高的上下文用满成本。
3. **预算**：是否批准 ① 的第二台评测 pod（约 $70–100 加 Modal），以及 ② 的 pilot（800 条轨迹）？全量筛（≤ 3.7K 条）等 pilot 结果出来再批。
4. **上下文**：第二轮是否允许偏离 64K（升到 128K，或者对上下文用满的轨迹做掩码）？两者都会改变训练和评测的口径，需要明确授权。
5. **评测口径**：TB2.1 改用 mean@8，并在开跑前预注册主指标和阈值，是否同意？
6. **ga103 的定位**：是否同意把它作为对照臂跑到 step 50，不中途改数据？
7. **B 组**：是否确认四个域继续由 baseline 线独立训练，不并入 A 组？Cyber 进入 A 组矩阵是否作为第三轮的候选？
