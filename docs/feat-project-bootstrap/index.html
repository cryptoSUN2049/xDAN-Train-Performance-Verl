来源 ↗

蒸馏 / SFT 学什么？

通过教师生成的任务求解示范，学习行动方式、工具调用和完成任务的模式。监督目标来自示范 token，而不是本次自主探索的成败。

Agentic RL 学什么？

模型在环境中自行行动，根据测试或 grader 的反馈调整策略。一个问题产生多条轨迹，比较结果后更新参数；训练数据会随策略变化。

不要把大模型路线直接套在 9B 上

MiMo 旗舰模型报告包含多领域混合 RL、GRS / GAR 等方法；§7 的 9B 开放基线是分别训练的领域 GRPO。若要声称某高级方法已进入公开 9B recipe，必须有相应代码证据。

Harbor、环境与 Pro 训练方法的边界

GRPO 是算法，Harbor 是任务执行/评测框架，两者不是替代关系。公开 9B 方案包含 mimoagent、K8s 任务 Pod、工具与 grader；当前审计的 recipe/依赖没有发现 Harbor 主训练链，General 仅见 manifest 对齐及迁移注释。它也不是 MiMo Pro 混合 RL、GRS/GAR、MOPD2 的完整缩小版。xDAN 若统一 Harbor 任务，应建立单独的环境适配层，并明确每项高级方法的实现与验收范围。

RESEARCH / 03

MiMo 全流程：从任务到参数更新

阅读这套方案的最短路径，是沿着“任务 → 执行 → 奖励 → 轨迹 → 更新”追踪每一个接口。

01 / INITIALIZE 装载 SFT 模型 tokenizer、chat template、reasoning 与工具协议必须对齐。
02 / SAMPLE 抽取任务与环境 读取 prompt 和任务元数据，选择 harness，准备任务沙箱。
03 / INTERACT 生成多条完整轨迹 模型输出行动，工具返回 observation，多轮运行至结束或预算耗尽。
04 / OPTIMIZE 评分与 GRPO 更新 归集 trajectory / reward，计算 advantage，更新 policy，重复下一批。

轨迹不只是最终答案

包括模型输出、工具调用、环境观察及终止状态。训练时需要区分参与 policy loss 的 token 与环境反馈；上下文预算和训练 token 数也不是同一个概念。

reward 不是脚本名称

Code 正常奖励来自 runner session 的 payload；小型 reward.py 是 fallback hook。main_ppo 或 reward_manager: dapo 的名字不改变已配置的 GRPO estimator。

完整数据闭环

展开公开数据的精确数量与真实文件布局

GRPO 与多 harness：分别优化什么？

一个优化“在同一任务上的行动”，另一个避免策略只适应单一执行框架。

Aᵢ ∝ rᵢ − mean(r₁, …, rG)概念示意：比较同任务一组 rollout 的奖励。是否除以组内标准差、如何归约及过滤，以具体 recipe 为准；不能将该式视为所有脚本的完整 loss。

同任务采样多条解法

Code / Cyber 参考组大小为 16，其余路线为 8。多条解法给相对比较提供信号，也成倍增加环境执行量。

Verifier 产生奖励

代码测试偏向可验证结果；知识工作依赖 rubric judge；网页还涉及视觉评审。评分服务不可用不能被当成模型失败。

根据 advantage 更新策略

奖励更优的行为获得正向学习信号。Code 的配置包含动态 group filter、prompt-mean 与关闭 GRPO 标准差归一化等细节。

进入下一轮，并独立评估

更新后策略继续生成新轨迹。训练 reward 上升不能单独证明能力提升，还要检查固定验证集、未见 harness 与失败率。

多 harness 实验，不是多个商业模型一起训练

Code 配置中的 mini-mimocode / mini-bash / mini-claude-code / mini-codex 是不同执行框架。它们通过统一模型网关使用 policy；名称不代表在训练四家商业模型。默认 step-hash 分配让同一 GRPO group 保持相同 harness，再随 step 轮换。

RESEARCH / 07

Ornith 深入拆解：从 self-scaffolding 到 self-improvement

这里解释作者公开的方法与证据缺口；方法级介绍不等于可下载的完整 9B 训练配方。

METHOD / 三个学习对象

不只优化答案，也优化“学什么”和“怎样解”

系统以环境或代码库、任务类型指令和既往解题历史为输入，提出新任务；再生成或改进 scaffold，最后让 policy 在这个框架内执行。反馈分别用于任务、harness 和解题 rollout 的 GRPO 优化。来源 ↗

INPUT 环境 + 解题历史 提供任务类型与当前能力的反馈。初始环境和数据来源仍需人为建立。
STAGE 1 Task proposer 提出可验证、有挑战且不重复的任务，把学习推向能力边缘。
STAGE 2 Scaffold / harness 构造指令、工具、任务分解、编排及评估环境。
STAGE 3 Solution rollout 执行解题并获得奖励，反馈推动下一周期的任务与策略改进。
已解决的任务变容易 → 难度奖励下降 → 任务生成器寻找新的、仍可学习的问题

三个奖励，承担三个不同责任

R_task = Validity × Difficulty × Novelty三个因素相乘：无效任务即使“很难”或“很新”，也不应得到高奖励。
信号 官方描述 工程含义
Validity · 有效且可验证 检查环境能执行、已知正确解通过、明显错误解失败、评估符合要求；可作为硬门槛。 先检查 grader，而不是让模型自己给自己高分。
Difficulty · 能力边缘 由当前 rollout 的成功率 p 衡量，目标 p* = 0.2；使用围绕目标的高斯形奖励。 成功率过高趋于饱和，过低缺少有效学习信号；0.2 是该文方法设定，不是通用定律。
Novelty · 非重复 与既往任务 buffer 中最相近任务的相似度相减。 降低重复题目占比；相似度实现和 buffer 规模未披露。
D = exp(−(p − 0.2)² / (2σ²))
N(q) = 1 − max similarity(q, previous tasks)公式按官方方法说明重排；σ、相似度模型及详细校准实现未在所查材料中披露。

Harness 奖励

任务对齐 × 奖励保真 × 抗作弊。评估器要反映任务目标，能区分解法质量，也要抵御利用评估器漏洞的行为。

需要独立检查机制；生成 harness 本身不保证奖励可靠。

Rollout 奖励

由 harness 评估实际解题结果。可验证任务可用二值成败；复杂任务可组合正确性、完成度、效率和约束满足。

博客称三阶段均用各自奖励进行 GRPO；未给出 9B 的完整优化参数或参数共享策略。

前代 Ornith 1.0：异步训练与反作弊边界

1.0 先根据任务和旧 scaffold 生成改进框架，再执行 rollout；解题反馈传到两个阶段。它已包含 RL，不能把 Ornith 1.0 称为 SFT 基线。

Pipeline-RL / token 陈旧度

旧策略产生的 token 随训练推进逐渐过时。官方描述使用分段权重：新鲜 token 保持权重 1，中间区间指数衰减，超过阈值置零；该权重乘在 token 级 GRPO 目标上。

K₁、K₂、λ 未给出具体值；不能断言 1.5 原样沿用所有设置。

三个不可省略的控制面

外部环境、工具面和测试隔离保持固定；确定性 monitor 将越界轨迹记零并排除 advantage；冻结 LLM judge 只作否决器。模型可改变内部记忆、错误处理与编排，不意味着任意修改外部 verifier。

Ornith 1.0 官方方法 ↗

1.0 → 1.5 的分数差是版本整体变化，不是新增 task generation 的单因素因果收益；所查材料没有足够消融来完成归因。

“自生成”不等于无数据，也不等于无需外部监督

种子环境、代码库、历史任务、有效性验证及 anti-hacking 检查仍然提供先验与约束。真正需要审计的是数据从哪里来、验证是否独立、评测是否隔离；不能仅用“self-improvement”替代这些证据。

选择与实施路线：先证明闭环，再扩规模

以下是工程建议，不是官方已验证的缩配方案；选择取决于你要交付模型、环境还是训练能力。

目标 A / 马上使用 Agent 模型

先做同条件推理评测

比较公开的 MiMo SFT 与 Ornith 1.5 权重。保持工具、任务、预算和超时一致，记录成功率、延迟、token 与工具错误。不能把未公开的 MiMo 领域 RL 权重当成可直接下载的候选。

目标 B / 建立 RL 训练能力

从 MiMo 单一领域切入

先验证一个任务镜像和 grader，再固定小任务集建立基线；保留完整轨迹。环境和奖励正确后，才开展短程参数更新与资源测量。

目标 C / 研究自改进方法

把 Ornith 思路作为实验变量

在可运行的闭环上逐步加入任务生成或 scaffold 优化，用消融实验验证。由于缺少完整原始数据配方，这属于方法再实现，不能直接宣称复现 Ornith。

建议里程碑与退出条件

阶段 交付物 通过条件
M0 · 固定证据 commit、模型 revision、数据 revision、配置与依赖清单 每个结果可定位到同一组输入资产
M1 · 环境与基线 单任务轨迹 + grader 日志；固定集 SFT 结果 成功/失败任务可重复评分；基础设施失败单独记账
M2 · RL smoke test 少量更新、checkpoint、独立评测记录 确有梯度/参数更新；轨迹可读；模型可恢复
M3 · 参考规模训练 固定预算运行、checkpoint 曲线、资源账单 无静默 grader 故障；训练与评测条件锁定
M4 · 报告级复现 同设置公开评测与偏差分析 给出多次运行波动；不以单次分数等同论文结果

投资判断：先验证“奖励是否可信”

模型不提升可能来自策略，也可能来自镜像、judge、共享存储或工具协议。先用已知成功/失败的轨迹检验 verifier，通常比立即加 GPU 更能减少无效实验。

长期建设决策：xDAN-Train-Performance-Verl

从小米公开方案起步，建设训练、性能与复现证据的平台；仓库已于 2026-09-28 建立；以下是尚待实施与验收的平台架构。

ARCHITECTURE DECISION / 建议采纳

建议 fork XiaomiMiMo/verl，建设 xDAN-Train-Performance-Verl。

长期建设的目标是：把模型、任务、环境、奖励、轨迹、训练和评测组织成可追溯的实验系统。小米代码提供可审计起点；xDAN 的长期资产应沉淀在可复现实验与性能证据上，而不只是仓库改名。

为什么现在值得 fork？

  • 已确定持续训练平台的目标，需要稳定保存上游修复、本地适配和实验版本。
  • 存在具体工程工作：公开数据布局适配、镜像映射、依赖锁定、预检查与评测规范。
  • 将内部复现经验留在有测试、有版本记录的配置和代码中，比复制零散启动脚本更可维护。

fork 的边界应保持克制

  • 第一阶段尽量不改 verl/ 核心；先扩展配置、适配器和运行记录。
  • 先锁定小米提交跑通一条路线，再扩到多领域，避免同时改训练、奖励和任务生成。
  • Ornith 当前主要作为方法参考与评测候选；fork 文档仓库不能替代它未开放的训练实现。

建议分层：核心上游化，能力扩展本地化

LAYER 1 上游训练引擎 verl / Megatron / SGLang；维护最小核心补丁，优先向适当上游回馈通用修复。
LAYER 2 环境与数据适配 任务 schema、镜像映射、harness、grader、基础设施预检。
LAYER 3 可追溯实验 冻结配置、revision、容器 digest、随机种子、checkpoint 与轨迹。
LAYER 4 性能与业务评估 能力、泛化、吞吐、成本、稳定性与奖励有效性，形成决策依据。

长期里程碑：每一阶段都需要可证据化的退出条件

阶段 核心工作 验收产物
P0 / 复现基线 版本锁定、单领域环境、数据与镜像适配、SFT 基线。 可重放任务轨迹、resolved config、独立 grader 检查；确认公开资产缺口。
P1 / 训练闭环 GRPO 短程训练、checkpoint 恢复、错误分类、固定集评估。 真实参数更新与恢复证据；能力、成本、失败率随 step 的记录。
P2 / 多模型多领域 扩展经过验证的 recipe；统一协议与评测预算。 可比较的实验矩阵；不会把各领域最好成绩拼成不存在的单模型。
P3 / 性能工程 吞吐、显存、环境并发、policy staleness 与成本优化。 每项优化有同配置对照；单位成功任务成本下降且能力不回退。
P4 / 自改进研究 逐步加入任务生成 / scaffold 优化；保持独立 verifier。 固定任务基线与消融，评测隔离及反作弊结果；标明是方法再实现。

Performance 的定义不能只有 tokens/s

能力与泛化

固定公开/业务集成功率、跨 harness 表现、未见任务、同预算多次评测波动。

训练与基础设施

有效训练 token 吞吐、峰值显存、rollout 延迟、队列等待、环境启动失败和超时率。

成本与收益

GPU-hours、CPU/存储、judge API 费用；每个成功任务的推理成本、达到既定能力增益的训练成本。

奖励与可追溯性

judge 可用率、奖励分布、过滤率、hacking 样本、配置/数据/模型版本覆盖率。

当前建议：同意项目方向，先投资可复现基线

最优起点是“一个领域、一组固定任务、一套可信 grader、一份可恢复训练记录”。只有当这些稳定后，才建设跨实验调度或可视化平台。需要进一步确定的是硬件预算、优先业务领域和仓库归属，它们不影响本报告对 fork 方向的判断。
